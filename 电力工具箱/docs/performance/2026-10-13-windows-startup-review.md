# Windows 启动问题复核与修复（2026-10-13）

依据：用户提供的 `01_错误日志原文.txt`、`02_性能实测数据.txt`、`03_诊断报告.md`，仓库 `v0.1.2` 标签源码及当前工作区。附件作为诊断材料核对，未直接执行其中的处置命令。

## 已确认的事实与证据边界

- 原始事件记录确认 Python 3.11.15 在 13:54:39 出现无响应，随后记录 AppHangB1；日志没有 Python 线程栈，无法据此定位具体阻塞函数。
- 实测材料记载清单文件 609/609 哈希匹配、没有缺失；未记录 Defender 查杀事件。此次未连接原 Windows 电脑重新校验。
- `v0.1.2` 与修改前工作区均在启动 300 毫秒后创建隐藏的 WPS 页面。这会引入页面模块加载、后台依赖导入和主线程控件构建，属于可以移除的启动负担。
- `v0.1.2` 已将 WPS 脚本导入放在工作线程，Tk 控件由主线程创建。因此“所有 WPS 重型依赖均在主线程串行导入”与源码不符；独立进程的不同导入计时也不能直接相加作为真实启动阻塞时间。
- WPS 写入使用 Playwright 操作金山文档，市场表、交易系统信息和功率收益表使用浏览器取数及 openpyxl 写表。所核对的实现没有 `win32com`、`xlwings` 或 `comtypes` 依赖；本机未安装 WPS Office 不能解释这些工具无法启动。
- Schannel 事件标明的客户端为 `backgroundTaskHost`、`SDXHelper`、`SearchHost`，没有工具箱进程证据，不能认定为工具箱更新请求失败或反复重试。
- 外壳为 Tauri，并非 Electron。`v0.1.2` 已在单实例回调中请求激活原 Tk 窗口；第二次双击无反应可能与 Python 无响应有关，不能简单归因于单实例只退出新进程。
- `v0.1.2` 已有 20 秒更新检查超时，没有自动反复检查逻辑。当前工作区另已有隐藏更新 webview、主窗口页脚进度、重复请求保护；这些是本次开始前的改动。

## 本次修改

- 删除主窗口的自动 WPS 预热定时器及相关清理逻辑。默认启动只显示“今日概览”，业务页面按首次访问创建并缓存。
- 保留 WPS 首次访问时的后台导入与主线程创建控件，避免把 Tk 页面构建移到工作线程。
- 同步桌面生命周期测试、性能测量脚本，补充真实事件循环下的启动延迟加载回归。
- 补充更新检查失败后只请求一次并恢复空闲状态、激活请求恢复隐藏主窗口的验证。
